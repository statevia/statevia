# spec-pick-next

完了直後・着手前などに、**次に着手する Spec / タスク**を根拠つきで提案し、ユーザーと合意する。

## 前提

- ワークスペースが statevia リポジトリであること。
- 次のいずれかの文脈があること（無い場合は索引から現状把握してよい）。
  - 直近完了した Spec / コミット / UAT
  - ユーザーが気にしている領域（Module / CLI / Engine / UI など）
- Markdown / Spec 更新が必要なら `.cursor/skills/markdown-spec-authoring/SKILL.md` に従う。

## 実行してほしいこと

1. **現状把握**（並列可）:
   - [`.spec/specs/spec-backlog-index.md`](../../.spec/specs/spec-backlog-index.md) の未掲載一覧と「次アクション」列
   - 関連する実施チェックリスト（どちらか／両方）:
     - [implementation-rollout-checklist-actions.md](../../.spec/specs/implementation-rollout-checklist-actions.md)
     - [implementation-rollout-checklist-safety.md](../../.spec/specs/implementation-rollout-checklist-safety.md)
   - 直近完了候補 Spec の `tasks.md`（未完了・Cancelled・委譲先の有無）
   - ユーザーが言及した依存・ブロッカー（手動 UAT、他 PR、未 push など）

2. **候補を 1〜3 件に絞る**:
   - **推奨 1 件**を先頭にし、根拠を短く書く（依存が揃っている／同一トラックの自然な続き／ブロッカー解消後など）。
   - 代替候補は「いつ選ぶか」を 1 行で添える。
   - 前提未充足・設計矛盾・legacy 互換の食い違いがある候補は、着手前に直す点を明示する（推測で実装方針を確定しない）。
   - 完了済みで索引が古い Spec は、次タスク候補ではなく **archive / 索引更新** として分けて書く。

3. **ユーザーへ確認**（独断で実装に入らない）:
   - 推奨 Spec のフォルダ名と、着手する最初のタスク番号（あれば）
   - 代替を選ぶ場合の条件
   - 併せてやるべきハウスキーピング（`/spec-archive`、backlog 更新、チェックリスト移管）があれば列挙
   - **判断はユーザーに委ねる**旨を明記する

4. **合意後のみ**（ユーザーが「これで」と指示したとき）:
   - 選んだ Spec の `tasks.md` Status / 着手ゲートを現状に合わせる（必要なら）
   - `spec-backlog-index.md` の該当行「状態」「次アクション」を更新する
   - チェックリストへ取り込む合意があれば、該当マトリクスへ移管し索引から削除する（二重管理を避ける）
   - 変更した Markdown は `npx markdownlint-cli2 "<パス>"` で確認する
   - 実装着手は別途の明示依頼があるまで行わない（本コマンドの主成果は **合意と索引整合**）

5. **報告**:
   - 推奨 / 代替の一覧
   - ユーザー確認待ちの論点
   - 合意済みなら更新したパス一覧

## 選定の目安（優先の考え方）

| 優先しやすい | 後回ししやすい |
| --- | --- |
| 直前 Spec の委譲先・前提完了の続き | 契約たたき台のみ（Engine 契約など） |
| 同一トラックで依存が揃っているもの | 正式リリース前の大きな DB 移行など |
| 運用ギャップが既にドキュメント化されているもの | 設計のみ・着手ゲート未通過 |

## ユーザー向け短文（チャットへの貼り付け用）

直近の完了状況と `spec-backlog-index` / ロールアウトチェックリストを見て、次に着手する Spec を 1〜3 候補で提案し、合意後に索引を更新してください。実装には入らないでください。
