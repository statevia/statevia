# git-branch-create

**新しい Git ブランチを作成する。** 名前は **`docs/development-guidelines.md` の「§6 ブランチ命名」**に従う。

**形式**: `<種別>/<短い説明-kebab-case>`

| 種別 | 用途（コマンド既定） |
| --- | --- |
| `feature` | 新機能・拡張・Spec 実装（**既定**） |
| `fix` | 不具合修正（文脈が明確なとき） |
| `chore` / `docs` / `test` | ガイドライン §6 のとおり（文脈が明確なとき） |

説明部は **英語 kebab-case**・**ASCII**・**1 ブランチ 1 目的**。  
**`~/` 接頭辞は使わない**（Git のブランチ名として無効。シェル展開とも衝突する）。

## 前提

- ワークスペースが **Git リポジトリ**であること。
- 同一チャットに、作業内容または `@` 参照（例: **`.spec/specs/`** 配下）が含まれることが望ましい。

## 実行してほしいこと

1. **仕様書フォルダの優先**  
   チャットや `@` 参照から、**`.spec/specs/<フォルダ名>/`** の仕様を **作成・修正している**ことが分かる場合は、説明部を **そのフォルダ名をそのまま**採用する（例: フォルダが `config-options-validation` なら第一候補は `feature/config-options-validation`）。複数 spec フォルダにまたがる場合は、**主に編集している 1 フォルダ**を優先し、必要ならユーザーに確認する。

2. **上記以外**  
   チャット文脈から作業内容を要約し、命名規則に合う **候補を 2〜3 個**挙げる（いずれも `<種別>/<説明-kebab-case>`）。チケット番号などが文脈にあれば **末尾に付与してよい**（ガイドライン §6 と同様）。

3. **確定**  
   推奨の 1 本を明示し、ユーザーに確認する。**ユーザーが別名を指定したらそれを優先**する。  
   確認なしで進めてよいのは、ユーザーが本コマンド実行時に別名を既に指定している場合、または直前ターンでブランチ名が合意済みの場合。

4. **ブランチ作成**  
   適切な起点（通常は現在の `HEAD`。`main` から切りたいなどの指示があれば従う）で、シェルから Git を実行する。例:

   ```bash
   git switch -c "feature/<説明-kebab-case>"
   ```

   **PowerShell** でもブランチ名は **引用符で括る**こと。

5. **結果**  
   作成したブランチ名と現在ブランチ（`git branch --show-current` 等で確認できる内容）を短く報告する。失敗時はエラーメッセージと次の一手を書く（無効な文字・既存ブランチなど）。

## ユーザー向け短文（チャットへの貼り付け用）

ブランチ名は `feature/<kebab-case>`（§6）。`.spec/specs/` の仕様作業ならそのフォルダ名を説明部にそのまま使い、それ以外は文脈から候補を出してブランチを作成してください。`~/` は使わないでください。
